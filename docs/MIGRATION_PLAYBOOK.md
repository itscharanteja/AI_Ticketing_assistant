# Migration Playbook

This playbook describes how agents should approach migrations for this project. It assumes the current system behavior described in `PROJECT_API_AND_FUNCTIONALITY.md`.

## Migration Goals

Most migrations should preserve:

- Existing ticket CRUD behavior.
- Existing AI processing behavior.
- Existing frontend user flow.
- Existing ticket status values.
- Existing API response field names.
- Existing local Docker Compose developer experience.

If a migration intentionally changes any of these, document the change and update all affected callers in the same work item.

## Recommended Migration Sequence

1. Baseline the current behavior.
2. Stabilize configuration and environment variables.
3. Migrate or refactor one service at a time.
4. Add compatibility tests before changing API contracts.
5. Move data schema with explicit migrations.
6. Migrate runtime orchestration.
7. Verify end-to-end ticket submission and dashboard behavior.
8. Update docs and handoff notes.

## Service Migration Notes

### Frontend

Current frontend responsibilities:

- Collect ticket title, description, and email.
- Create ticket through Ticket Service.
- Call AI Service to process the ticket.
- Show success or escalation messages.
- Display dashboard with auto-refresh.
- Delete tickets after confirmation.

Migration risks:

- `frontend/src/App.js` uses hardcoded submit URLs for Ticket Service and AI Service.
- The email field is required by the UI but not stored by Ticket Service.
- If AI processing fails after ticket creation, the ticket remains `open`.
- Dashboard only reads Ticket Service and does not call AI Service.

Migration actions to consider:

- Replace hardcoded URLs with `REACT_APP_*` values.
- Consider moving create-and-process orchestration into a backend endpoint.
- Preserve dashboard polling or replace it with a documented real-time mechanism.

### Ticket Service

Current Ticket Service responsibilities:

- Health check.
- Ticket CRUD.
- PostgreSQL persistence through Sequelize.
- Basic required-field validation on create.

Migration risks:

- Schema is created with `sequelize.sync()` rather than migration files.
- The update route uses truthiness fallback and cannot clear fields.
- Status validation mostly relies on the database enum.
- Email is not stored.

Migration actions to consider:

- Add explicit migration files before production migration.
- Verify actual PostgreSQL schema generated by Sequelize.
- Add request validation for update and status transitions.
- Decide whether email belongs in the ticket model.

### AI Service

Current AI Service responsibilities:

- Health check with RAG metadata.
- Process tickets with SmartRAGEngine and Anthropic Claude.
- Update Ticket Service status and `ai_response`.
- Send AI-response or escalation emails.
- Add and search in-memory knowledge entries.

Migration risks:

- Missing `ANTHROPIC_API_KEY` exits the service at startup.
- Runtime RAG implementation in `server.js` differs from exported `SmartRAGEngine.js`.
- Knowledge base is in memory only.
- Escalation is detected from generated text using `/escalat/i`.
- Ticket update failures and email failures are logged but do not fail the response.
- `email_sent` can be `true` even when email sending failed.

Migration actions to consider:

- Unify SmartRAGEngine implementations.
- Add durable knowledge storage.
- Use structured AI output for status decisions.
- Make ticket update failures visible or retryable.
- Return accurate email status.

## API Compatibility Checklist

Before and after migration, verify these endpoints if they are still in scope:

Ticket Service:

- `GET /health`
- `GET /tickets`
- `GET /tickets/:id`
- `POST /tickets`
- `PUT /tickets/:id`
- `DELETE /tickets/:id`

AI Service:

- `GET /health`
- `POST /process-ticket`
- `POST /add-knowledge`
- `POST /search-knowledge`

Frontend workflows:

- Submit ticket that becomes `auto-resolved`.
- Submit ticket that becomes `escalated`.
- View dashboard ticket counts.
- Delete a ticket.
- Recover gracefully when AI processing fails.

## Data Migration Checklist

- Export current ticket rows.
- Confirm actual table and column names in PostgreSQL.
- Preserve `id` values if external references exist.
- Preserve `created_at` and `updated_at` values if analytics or audit history matter.
- Preserve `ai_response` text exactly.
- Preserve status enum values.
- Decide whether to backfill email if a new schema adds it.

## Configuration Checklist

- Browser-facing frontend URLs:
  - `REACT_APP_TICKET_API_URL`
  - `REACT_APP_AI_API_URL`
- Container-internal service URL:
  - `TICKET_SERVICE_URL`
- Database:
  - `DB_HOST`
  - `DB_USER`
  - `DB_PASS`
  - `DB_NAME`
- AI:
  - `ANTHROPIC_API_KEY`
  - `CLAUDE_MODEL`
- Email:
  - `SMTP_HOST`
  - `SMTP_PORT`
  - `SMTP_USER`
  - `SMTP_PASS`

## Done Criteria

A migration task is complete only when:

- Affected tests pass or skipped checks are explained.
- API behavior is preserved or documented.
- Data migration impact is known.
- Environment variable changes are documented.
- Docker/local startup impact is known.
- Handoff notes include remaining risks.
